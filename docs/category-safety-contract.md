# Category safety contract

This document defines the evidence and risk rules used before adding or widening a cleanup category. It is intentionally conservative: a large directory is not proof that it is safe to delete.

## Contract

Every category must document:

| Field | Requirement |
| --- | --- |
| Matcher | Exact path or filename rule; avoid a broad basename unless evidence is available. |
| Evidence | Project or tool marker that makes regeneration plausible. |
| Risk | low, review, or opt-in. |
| Regeneration | The command or tool operation that recreates the data, when known. |
| Never delete | User data, source files, credentials, lockfiles, or tool state that is not disposable. |
| Fixtures | Positive and negative examples on supported operating systems. |

### Risk levels

- low: an exact, tool-owned disposable cache with strong evidence. It can appear in normal analysis.
- review: regenerable output that can be expensive or surprising to recreate. It appears with an explanation and remains subject to review.
- opt-in: broad or ambiguous matches. It is excluded from normal cleanup unless the user explicitly enables the category.

Risk is a product-safety decision, not a size threshold. The CLI must never infer safety from bytes alone.

## Current migration rule

Existing category keys are part of the report and CLI contract. New evidence checks must not silently reinterpret an existing key. When behavior changes, document the migration and add fixtures for both:

1. a supported project with the expected marker and disposable artifact;
2. an unrelated directory with the same basename and no marker.

Until a category has evidence-driven matching, it remains review or opt-in.

## BDD scenarios

### Recognized project artifact

Given a directory containing Cargo.toml and target/  
When reclaimit analyzes its parent  
Then target/ is classified as a Rust build artifact  
And the report explains that it can be regenerated by Cargo.

### Unrelated directory

Given $HOME/build/ without supported project evidence  
When reclaimit analyzes $HOME  
Then the directory is not a default cleanup candidate.

### Broad cache

Given a project-local .cache/ with no recognized tool marker  
When reclaimit analyzes the project  
Then the category follows its documented risk level  
And cleanup requires the normal review and confirmation flow.

## Implementation checklist

Before merging a category change:

- add the matcher and risk metadata;
- add positive and negative fixtures;
- verify nested-candidate de-duplication and repository grouping;
- document regeneration cost and exclusions;
- keep every production source file above 90% coverage;
- do not add telemetry or treat size as evidence.
